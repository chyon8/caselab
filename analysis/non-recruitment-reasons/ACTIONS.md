## 2. 상세 정보 미작성 제출 — 결론: 원인 분석에서 제외 (2026-10-01)

- 상세 항목(직군·기획 상태 등)은 **고객이 등록할 때 입력하고, 비어 있으면 검수 중에 매니저가 채운다**(사용자 확인). 그래서 지금 비어 있는 건은 «검수가 진행되지 않은 건»이고, 모집 0건은 원인이 아니라 결과다. 제출 시점에 고객이 입력했는지는 지금 데이터로 구분할 수 없다.
- 간편상담 여부도 본진 데이터와 관리자 화면으로 구분할 수 없다(사용자 확인). `free_consulting_requestconsulting`(무료 상담)에는 프로젝트 번호가 없고, `anonymous_client_uuid`(비회원 제출, 26%)는 간편상담 표시가 아니다(비회원이어도 상세 정보가 있으면 51% 모집).
- 그래서 «간편상담 없애기» 후보는 데이터로 판단할 수 없어 보고서에서 뺐다. 직군 «미입력»·대표 분야 «미상»도 같은 이유로 원인으로 읽지 않는다.
- 부수 발견: 등록 시 **연락 가능 시간**(`inspection_contact_datetime_string`)과 **즉시 연락 희망**(`is_inspection_contact_asap`)을 받고 있다. 외주 전체 제출 기준 연락 안됨 비율은 입력 안 함 12.2%(2,467건) / 시간대 입력 8.7%(1,291건) / 즉시 연락 희망 4.3%(1,034건), 모집 비율 36.8% / 48.6% / 54.6%. 보고서 후보 A에 반영했다. 매일 추적하려면 n8n SQL에 두 값을 싣는 것을 검토한다.

### 2-1. 제출 유형 구분 — 해결 (2026-10-01)

- 고객이 제출할 때의 원본은 본진 `submit_temporaryproject`(project_id로 연결, 원래 `title`·상세 항목 보존)에 있다. 모집 시 매니저가 제목을 바꾸므로 `project_project.title`로 나누면 안 된다.
- 원래 제목 `[간편 상담 신청]` = 별도 간편 상담 폼, `[상담 신청]` = 프로젝트 등록 폼을 중간까지 쓰고 «여기까지 작성 후 제출», 접두어 없음 = 등록 폼을 끝까지 작성(사용자 확인 2026-10-01).
- 결과(2026-01 이후 외주 4,792건): 끝까지 작성 2,378건 모집률 70.1% / 중간 제출 1,679건 40.8% / 간편 상담 732건 39.7% (유효 제출 기준). 중간 제출은 연락 안됨 19.3%·무효 거절 20.8%, 간편 상담은 견적·단순 문의 8.7%가 두드러진다. 보고서 «2. 제출 유형», 후보 B에 반영.
- 다음(제안): n8n 일일 SQL에 원본 제목의 유형만(`submit_kind`) 실어 화면에서 유형별로 나눠 보기. 원본 제목 텍스트는 싣지 않는다.

## 3. 중복 등록 경고

- 현황: 무효 거절 중 중복 등록·어뷰징 285건(무효 거절 1위), 모집 전 직접 취소 중 «중복 등록» 22건, «실수로 등록» 111건.
- 알고 싶은 것: 제출 시점에 같은 고객이 최근 30일 안에 다른 외주를 낸 경우가 얼마나 되고, 그중 몇 건이 중복으로 끝나는지. 이 비율이 높으면 제출할 때 경고를 띄우는 것으로 대부분 막을 수 있다.

```sql
SELECT t.has_recent, COUNT(*) AS submitted, SUM(COALESCE(t.dup_reject, 0)) AS dup_reject, SUM(t.dup_cancel) AS dup_cancel, SUM(t.mistake_cancel) AS mistake_cancel
FROM (
  SELECT pp.id,
    EXISTS (SELECT 1 FROM project_project o WHERE o.client_id = pp.client_id AND o.id <> pp.id AND o.project_type = 'task_based' AND o.date_submitted < pp.date_submitted AND o.date_submitted >= pp.date_submitted - INTERVAL 30 DAY) AS has_recent,
    (SELECT CASE WHEN TRIM(il.note) LIKE '중복%' OR TRIM(il.note) LIKE '프로젝트 중복%' THEN 1 ELSE 0 END FROM process_log_inspectionlog il WHERE il.project_id = pp.id AND il.status = 'reject' ORDER BY il.id DESC LIMIT 1) AS dup_reject,
    CASE WHEN pp.cancel_type LIKE 'duplicate%' THEN 1 ELSE 0 END AS dup_cancel,
    CASE WHEN pp.cancel_type LIKE 'add_mistake%' THEN 1 ELSE 0 END AS mistake_cancel
  FROM project_project pp
  WHERE pp.project_type = 'task_based' AND pp.date_submitted >= '2025-12-31 15:00:00' AND pp.client_id IS NOT NULL
) t
GROUP BY t.has_recent
```

- **결과(2026-10-01):** 중복 거절 286건 중 같은 계정의 30일 내 외주 제출이 있던 건 129건(45%). 조건에 걸리는 제출 717건 중 중복으로 끝난 건 139건(19%). «실수로 등록» 취소 113건 중 95건은 조건에 안 걸린다. → 같은 계정 경고로는 중복의 절반 정도만 막고, 경고의 80%는 정상 재제출에 뜬다.

|---|---|---|

## 5. 연기 고객이 다시 오는지

- 현황: «프로젝트 연기» 141건, «프로젝트 취소» 131건. 같은 프로젝트가 나중에 살아난 건은 연기 4건(평균 29일 뒤)뿐이다(§6). 다른 프로젝트로 다시 제출하는지는 고객 단위로 봐야 해서 본진에서만 볼 수 있다.
- 아래 SQL은 거절일로부터 180일 안에 같은 고객이 외주를 다시 제출했는지, 그게 모집됐는지를 사유별로 센다. 최근 거절은 180일이 다 안 지나서 낮게 나온다.

```sql
SELECT t.reason, COUNT(*) AS rejected, SUM(t.came_back) AS came_back, SUM(t.came_back_recruited) AS came_back_recruited
FROM (
  SELECT pp.id,
    (SELECT CASE WHEN TRIM(il.note) LIKE '프로젝트 연기%' OR TRIM(il.note) LIKE '프로젝트 보류%' THEN '프로젝트 연기' WHEN TRIM(il.note) LIKE '프로젝트 진행 취소%' OR TRIM(il.note) LIKE '취소%' THEN '프로젝트 취소' WHEN REPLACE(TRIM(il.note), ' ', '') LIKE '연락안됨%' THEN '연락 안됨' WHEN TRIM(il.note) LIKE '재연락%' THEN '재연락 후 두절' WHEN TRIM(il.note) LIKE '견적 문의%' OR TRIM(il.note) LIKE '단순 문의%' THEN '견적·단순 문의' WHEN TRIM(il.note) LIKE '단가%' THEN '단가 안 맞음' WHEN TRIM(il.note) LIKE '기획 및 내용%' THEN '기획 구체화 필요' ELSE '그 외' END FROM process_log_inspectionlog il WHERE il.project_id = pp.id AND il.status = 'reject' ORDER BY il.id DESC LIMIT 1) AS reason,
    EXISTS (SELECT 1 FROM project_project o WHERE o.client_id = pp.client_id AND o.id <> pp.id AND o.project_type = 'task_based' AND o.date_submitted > pp.date_rejected AND o.date_submitted <= pp.date_rejected + INTERVAL 180 DAY) AS came_back,
    EXISTS (SELECT 1 FROM project_project o WHERE o.client_id = pp.client_id AND o.id <> pp.id AND o.project_type = 'task_based' AND o.date_submitted > pp.date_rejected AND o.date_submitted <= pp.date_rejected + INTERVAL 180 DAY AND o.date_start_recruitment IS NOT NULL) AS came_back_recruited
  FROM project_project pp
  WHERE pp.project_type = 'task_based' AND pp.is_rejected = 1 AND pp.date_start_recruitment IS NULL AND pp.date_rejected IS NOT NULL AND pp.date_submitted >= '2025-12-31 15:00:00' AND pp.client_id IS NOT NULL
) t
GROUP BY t.reason
ORDER BY rejected DESC
```

- **결과(2026-10-01, 거절 후 180일 내 같은 고객 재제출 / 그중 모집):** 연락 안됨 449→21/9, 연기 140→8/6, 견적·단순 문의 131→13/2, 단가 123→6/3, 프로젝트 취소 118→5/3, 기획 구체화 98→7/5, 재연락 후 두절 82→2/0. 돌아오는 고객은 5% 안팎, 연기·기획 부족 고객은 돌아오면 대부분 모집.

## 7. 첫 이용 고객 안내 실험

- 기준선(2026-01~09): 위시켓 모집 경험이 없는 고객의 유효 제출 2,942건(월 약 330건), 거절률 47.2%. 사유는 연락 안됨 14.6%, 프로젝트 연기 4.4%, 견적·단순 문의 4.2%, 프로젝트 취소 4.1%, 단가 3.6% (유효 제출 대비).
- 안내 예시: 제출 직후 «검수 절차, 연락이 오는 시점과 방법, 예상 단가 범위(§1)»를 메일·문자로 보낸다.
- **실험 규모(50:50 나눔, 유의수준 5%, 검정력 80%)**

| 기대 효과 | 그룹당 필요 | 기간(월 330건 기준) |
|---|---|---|
| 거절률 10%p 감소 (47→37%) | 약 380건 | 약 2.5개월 |
| 5%p 감소 (47→42%) | 약 1,550건 | 약 9.5개월 |

- 실험 없이 전후 비교만 하면 계절 변화와 섞인다. 나눠 보내는 게 어렵다면 시작일을 기록하고 «미모집 사유» 화면에서 전후 3개월을 비교한다.
- 필요한 것: 안내 문구, 발송 방법, 시작일. 사업·운영 쪽 결정이다.
