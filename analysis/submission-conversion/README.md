# 제출→모집 패턴 분석 실행 계획

기준일 **2026-09-22**. 목적은 고객·프로젝트 특성과 모집 전환의 **관측된 관계**를 비교하고 후속 실험 후보를 만드는 것이다. 유효한 차이·타깃 후보가 0개여도 분석 실패가 아니다. 과거 답변의 '3~5개 가설 도출'은 목표 개수에서 제외한다.

## 0. 실행 우선순위 — 회사에서는 수집, 집에서는 분석

**사용자 제약 반영:** 본진 DB는 회사에서만 접근 가능하고 연휴·주말에는 집에서 작업할 수 있어야 한다. 인벤토리 66개는 누락 방지 목록이지 이번 마감까지 전부 구현할 할당량이 아니다. **핵심 자료 확보 → 사외 접근 검증 → 분석** 순서가 아래 상세 계획보다 우선한다. 새 파이프라인·화면 개발, 외부 기업정보 보강, 첨부/통화 전량 판독은 이번 선행 작업이 아니다.

### 회사에서 끝낼 순서

1. **기존 연결 확인:** 본진 `/query`에 접근 가능한 n8n 노드와 CaseLab 동기화 키를 재사용한다. 기업 규모·추가 DB는 이번 선행조건에서 제외한다. DB 비밀번호나 개인정보를 대화에 붙이지 않는다.
2. **분석 전용 적재:** `submission_analysis_backfill.sql`을 200건씩 읽어 전용 API/테이블에 저장한다. 기존 `03_base_extract.sql`이나 운영 `projects` 동기화로 대체하지 않는다.
3. **핵심 분석 묶음 저장:** 아래 원장·텍스트·코드 정의를 같은 추출 기준으로 CSV/JSONL에 확보한다. 문서/원문은 집에서 읽더라도 접근 가능한 사본 확보와 비식별화는 회사에서 한다. 추가 필드 탐색 때문에 핵심 추출을 미루지 않는다.
4. **퇴근 전 검증:** DB COUNT와 파일 고유 프로젝트 수 일치, 모집/거절/취소/대기 포함, 한글·긴 원문 잘림·연결키·누락 점검. 실제 집 작업 기기와 회사망 밖의 승인된 접속 방식에서 파일/필요 첨부를 열어 본다. 사내 링크·만료 URL만 있는 것은 확보 완료가 아니다.

| 순위 | 확보할 데이터 | 범위·처리 |
|---|---|---|
| 먼저 | 전체 제출 원장·결과 | 1~8월 외주 **전체 제출**의 ID, 제출/모집/거절/취소 시각·상태·사유 코드와 설명. 미전환/대기를 제외하지 않음 |
| 먼저 | 초기 프로젝트 내용·수치 | 당시 원문, 초기 예산·기간, 확보 가능한 유형/범위, 원본 생성·수정시각, 첨부 목록·생성/삭제시각. 현재 공고로 대체 금지 |

첨부는 메타데이터를 우선 확보하고, 내용 판독이 필요한 파일은 결과에 치우치지 않게 정한 표본의 허용된 사본/비식별 추출문을 확보한다. 일괄 확보가 간단하고 승인 범위 안이면 함께 보존하되, 비용 큰 OCR·판독은 집에서 판단한다. 원본을 사외 처리할 수 없으면 해당 내용 분석은 제외한다.

분석 묶음에는 사용 쿼리·기간·기준시각·시간대·파일별 건수/해시·필드 설명·미확보 목록을 붙인다. 고객키/해시 고객키·연락처·이름은 반출하지 않고 텍스트도 비식별화한다. 저장소/Git·개인 클라우드에 원자료를 넣지 않는다. 승인 경로가 없으면 접근통제를 우회하지 않고 사내 분석/승인된 원격 환경을 확인한다.

### 집에서 진행할 것

확보된 구조화 항목은 가능한 전량 집계한다. 원문은 **목적·과업/범위·구체성 등 핵심 문항과 검증 표본부터** 판독하며, 일정이 부족하면 상세 라벨/첨부 분석을 줄이고 검증 조건은 유지한다. 모집 전환과 검수 거절/취소를 같은 기준으로 비교해 건수·전환율·차이·불확실성을 내고, 충분히 관찰된 계약 결과를 보조 확인한다. 외부 DB가 늦으면 확보된 핵심 자료로 먼저 진행한다.

관찰 종료는 **실제 저장된 스냅샷 시각**이다. 9/29 보고한다고 그날까지 결과를 자동으로 아는 것이 아니므로, 재추출하지 못하면 회사에서 마지막으로 확보한 시점까지만 분석한다.

- 본 분석: **KST 2026-01-01 00:00 이상, 2026-09-01 00:00 미만에 제출한 외주**. 사용자 선택.

- 이번에는 일괄 추출→분석 파일→보고서로 진행한다. 새 상시 파이프라인·앱 화면·API·DB 마이그레이션은 필요하지 않다. 정기화를 결정하면 같은 데이터 계약을 재사용한다.

## 3. 확보 순서와 통과 기준

### G0 — 최신 스키마와 사건 의미 확인

담당: 기존 본진 스키마와 첫 배치 결과를 분석자가 대조한다. 사용자에게 새 스키마 제공을 요구하지 않는다.

1. `01_schema_audit.sql` 실행 결과로 테이블·컬럼·키·타입을 확인한다. 검색어에 걸린 후보만으로 의미를 확정하지 않는다. JSON이면 키와 질문 문구·선택지·버전을 확인한다.
2. 각 원천에 **행 단위(project/고객/응답/제출회차), 연결키, 기본값, 필수/선택, 수집 시작일, 값 수정 방식, 당시 값 복원 가능 여부**를 기록한다.
3. 제출일·모집일이 최초인지 최근인지, 재제출 시 덮어쓰는지, 취소/거절 코드와 날짜가 어떤 사건인지 확인한다. 초기 스냅샷도 재작성될 수 있으므로 저장 로직/실제 이력으로 검증한다.
4. 기존 본진의 상세 필드는 생성·수정 시각이 없을 수 있으므로 T0 확정값으로 바로 쓰지 않는다. 새 스키마 탐색 때문에 전체 원장 수집을 늦추지 않는다.

**통과:** 실제 필드별 원천 매핑표와 사건 의미 확인. 새 필드 미확인은 해당 가지를 보류하되 기본 표본 조사는 진행한다. 전체 제출 분모/사건 시점 자체가 검증되지 않으면 전환율 발표는 보류한다.

### G1 — 분모·원본·충족률 감사

`02`, `04`를 실행한다. 신규 DB 필드도 **제출 월(9월은 일)×결과 집단×폼 버전**으로 대상 수·유효값·미수집·미응답·시점불명·충돌 비율을 낸다. 규모가 채워진 행만 뽑아 비교군을 만드는 것은 금지한다.

- 모집/거절/고객취소/대기 각각 10건(10건 미만이면 전량)을 어드민과 대조한다. 재제출·숨김·삭제·날짜 충돌·초기 스냅샷 수정 사례는 별도로 모두 유형 확인한다.
- `project_id` 유일성, 1:N 조인 전 집계, 분모 누락, 페이지별 수신 수, 원천 COUNT와 추출 고유 ID 수 일치를 확인한다.
- 초기 원문 없는 행과 실제 빈 원문, 최초 예산 미기록 0과 실제 금액, 파일 미연결과 실제 0개를 구분한다.
- 직접 `project_id`가 없는 임시 첨부도 원천 매핑을 점검한다. 연결이 완전하지 않으면 SQL의 파일 수는 '직접 연결된 파일 수' 참고값으로만 사용한다.
- `detail_projectdetail` 현재값은 문서상 수정시각도 없다. 당시 폼 응답/이력 증명 전에는 초기 특성으로 승격하지 않는다.

**통과:** 분모 대조와 원본 시점이 확인된 변수만 주 분석에 채택. 특정 변수의 자료가 없다면 `측정 불가`를 산출물로 남긴다. 수집 방식이 결과 집단별로 다르면 차이를 원인으로 해석하지 않는다.

### G2 — 데이터·분류 정의 동결

최초 추출의 시작/종료 시각과 최종 관찰 기준 `as_of_utc`를 기록한다. 사건일이 기준일 이후인 값은 쓰지 않는다. 기준시각을 지나 수정된 행·배치 간 서로 다른 버전은 대조 후 최종 스냅샷을 고정한다. 이력이 없어 기준시점 복원 불가하면 해당 상태를 미상으로 둔다.

분석 원장·원문·매핑·코드북·쿼리·입력파일 해시·제외목록에 버전을 부여한다. 데이터 보완은 새 버전으로 합치고 기존판을 덮어쓰지 않는다. 결과를 본 뒤 분류 경계·예산 구간을 바꾸면 기존 정의의 결과도 보존하고 새 결과는 추가 탐색으로 표시한다.

**통과:** 다음 분석자가 동일 파일과 정의로 같은 분모/분자를 계산할 수 있음. 분류 교정·대표 검증은 CODEBOOK의 40건+80건 이중 판독 절차를 따른다. 실제 시간은 첫 10건에서 측정하고, 읽는 항목 수를 줄이더라도 동일 항목의 검증 기준을 느슨하게 만들지 않는다.

**원문 분류 규모:** 구조화 값은 전량 집계한다. 수작업 원문 분석의 기본 범위는 대표 검증 80건이며 그 범위를 결과에 명시한다. AI 보조 전량 분류는 선택 가능한 확장안으로, 사용자 선택·원본 처리환경·비용·변수별 정확도를 확인한 뒤 실행한다. 선택 전 유료 호출이나 외부 첨부 전송을 시작하지 않는다. 전량 적용 시에도 실패/누락 건을 음성으로 채우지 않고, 긴 본문/첨부의 미판독 범위와 모집·거절 양쪽의 오류율을 따로 보고한다.

## 4. '준비도'와 프로젝트 내용의 분석 정의

합산 준비도 점수·임의 가중치·좋은 고객 등급을 만들지 않는다. [CODEBOOK](CODEBOOK.md)이 각 변수의 단일 정의다.

| 축 | 측정할 것 | 관측되었다고 말할 수 없는 것 |
|---|---|---|
| A. 제출 정보의 표현 | 목적·사용 상황·기능 동작·범위 경계의 명시 수준, 실제 초기 첨부 | 긴 글/첨부만으로 추진 능력·발주 의지가 높음 |
| B. 실제 추진 여건의 기록 | 집행 예산·승인·담당자/개발자·착수 조건·보유 자산의 명시적 근거 | 미언급이므로 인력/예산/계획이 없음 |
| C. 프로젝트 내용 | 신규/고도화/유지보수, 의뢰 업무, 해결할 업무 문제, 산출물, 기존 시스템·연동·이전·제조/기술 제약 | 웹/앱 같은 대분류만으로 수요·전환 특성을 설명함 |
| D. 고객 배경 | 개인/법인, 제출 이전 외주·플랫폼 이용 경험, 유입 경로 | 법인=대기업, 계약 이력 없음=외주 경험 없음 |

**짧은 글도 비교에서 남긴다.** 확보한 원문에 목적이 없으면 A축의 `no_stated_purpose`이고, 원문 자체를 못 구했으면 `unavailable`이다. 내용이 빈약하지만 전환된 사례도 동일하게 포함한다. B축의 예산/개발자 미언급은 실제 여건 미상이다. 첨부 파일명만 보고 기획서로 확정하지 않는다.

기본 비교는 **T0 제출 시점에 알 수 있었던 정보**다. T1 검수 중에 새로 드러난 정보와 T2 사유/사후 노트는 별도 파일·표로 유지한다. 현재 상세정보/나중 통화에서 얻은 답을 모집 전환 건에만 보충해 T0와 합치지 않는다. 기존 공고 Completion 점수·AI 자기 confidence는 이 분석의 준비도/신뢰도가 아니다.

## 5. 분모·결과·시간 처리

### 분석 단위

- 주 원장: 프로젝트 ID당 최초로 복원 가능한 제출 1회. 같은 ID 재제출은 이력을 복원해 최초 제출을 확인하며 모집은 최초 도달 시점으로 계산한다. `date_submitted`가 최근 재제출로 덮였다면 현재값으로 최초인 것처럼 처리하지 않는다.
- 새 ID로 재등록/분할한 경우 기본은 각각 제출 건이다. `previous_project_id` 연결이 완전하면 연결된 최초 건만 남기는 민감도 표를 별도로 낸다. 제목이 같다는 이유로 합치지 않는다.
- 숨김/삭제·고객 실수/테스트성 제출도 기본 분모에서 임의로 빼지 않는다. 확인된 사내 QA 계정 건도 포함/제외 건수와 양쪽 결과를 따로 제시한다. 사유가 불편하다는 이유로 실수 등록을 배제하지 않는다.
- 제출 시점 복원 실패로 대상 기간 소속을 모르면 `scope_unknown` 목록을 만든다. 그 규모를 숨기고 전체 제출 전환율로 발표하지 않는다.

### 지표

| 지표 | 분모 | 분자/처리 |
|---|---|---|
| 14일 내 모집 전환율(주 기술지표) | 제출 후 14×24시간 관찰 가능한 전체 제출 | 제출 이상, 제출+14일 이하에 최초 모집 도달 |
| 7일·30일 내 모집 전환율 | 각각 해당 기간 관찰 가능한 제출 | 같은 정의. 14일은 업무 SLA/영구 성공 기준이 아니라 분석의 고정 관찰창 |
| 기준일까지 누적 모집 전환율 | 전체 제출, 경과일별/월별 함께 표시 | 기준일까지 한 번이라도 모집 도달. 관찰 기회가 다른 집단끼리 단독 순위 금지 |
| 검수 거절/고객 취소 구성 | 같은 관찰창에서 모집 전 종료한 프로젝트 | 거절·고객 취소는 별도. 최초 종료 사유와 이후 재개 여부 보존 |
| 90일 내 플랫폼 계약률 | 제출 후 90일 관찰 가능한 동일 제출 집단 | 실제 최초 유효 체결일이 제출 후 90일 이내 |

모집 후 취소도 제출→모집은 성공이다. 거절 후 재개해 창 안에 모집되면 전환 성공으로 세되 '모집 전 거절 이벤트 있었다'를 보조표에 보존한다. 창 안에 모집되지 않은 건은 거절·취소·대기·상태불명으로 나눈다. 대기를 영구 실패/거절로 부르지 않는다.

상태만 모집 이후인데 모집일이 없거나 날짜 역전/이력 충돌이면 해당 고정창 결과는 `unknown`이다. 대상 전체 N, 확인 성공 S, 확인 비전환 F, 결과 미상 U를 모두 내고 `S/N ~ (S+U)/N` 관측 한계 범위를 표시한다. U>0이면 단일 확정 전환율·그에 대한 통계 CI를 내지 않는다. 이 범위는 95% CI가 아니다.

계약 생성일/진행 시작일을 체결일로 대체하지 않는다. 특약 여러 개는 프로젝트 1건으로 집계한다. `date_contracted`는 DATE이므로 달력 기준을 확인하고 당일 제출 전후 또는 90일 경계가 모호하면 경계 건수를 따로 표시한다. SQL 03의 계약 후보값은 **현재** hide/deleted 조건의 영향을 받아 당시 계약 경험·계약 도달 사실의 확정값이 아니다. 상태 이력/숨김·삭제 계약 대조를 통과하기 전에는 해당 계약 분석을 보류한다.

## 6. 비교표와 신뢰도

### 비교표 생성 규칙

1. 구조화/검증된 모든 P1 변수의 모든 범주 결과를 공개한다. P2는 데이터가 채택 기준을 통과한 경우 추가하고, 제외 이유도 목록으로 남긴다.
2. 해당 범주 vs **같은 코호트·폼 노출·관찰창·자료 접근 범위에서 해당 변수 값이 관측된 나머지 집단**을 비교한다. 불명/미수집은 별도 행. A축의 관측된 표현 없음은 정상 비교값이다.
3. 다중 라벨은 프로젝트 중복을 제거하고 라벨별 있음/명시 또는 판독상 없음으로 비교한다. 서로 겹치는 라벨의 구성비 합은 100%가 아닐 수 있다.
4. 전체 프로젝트의 N/전환 수/전환율/차이(%p)/비교군 수와 누락률을 먼저 제시한다. 월별, 신규/재이용, 원본 확보 여부, 첫 고객 제출만, 관찰창 7/14/30일의 방향도 같이 확인한다. 서로 반대면 그대로 보고하고 하나의 '고전환 유형'으로 합치지 않는다.
5. 단순 비교와 교란을 구분한다. 산업·유입·시기·예산·자료수집 차이를 통제하지 못했다면 인과 원인/독립 효과로 말하지 않는다. 이번 기본 산출물에 다변량 예측모델·고객 점수·임베딩 군집은 포함하지 않는다.

### 반복 고객과 통계적 불확실성

전체 기간의 실제 전환 건수·비율은 확보한 데이터의 기술통계다. 미래 고객으로 일반화할 불확실성은 다른 문제다. 반복 고객의 여러 프로젝트를 독립 표본으로 취급해 좁은 신뢰구간을 붙이지 않는다. [Cameron·Miller의 원문](https://cameron.econ.ucdavis.edu/research/Cameron_Miller_JHR_2015.pdf)

기본 실행안은 본진에서 결과와 무관하게 **고객별 코호트 첫 제출 여부만** 계산해 내려받는 것이다(동시 제출이면 작은 프로젝트 ID). 원 고객키/해시 고객키는 반출하지 않는다. 고객키가 없는 건과 동일 회사 여러 계정의 잔여 의존성도 한계로 표시한다. 신규 9/3 코호트는 자기 기간 안의 첫 제출 플래그를 다시 계산한다.

- 전체 프로젝트 표: 기술통계와 데이터 품질. 반복고객 보정 CI를 계산하지 않았다고 명시.
- 고객별 첫 제출 표: **결과가 알려졌는지와 무관하게** 첫 제출·비교군을 먼저 고정한다. 고객키/독립성 조건이 검증되고 양 집단 모두 U=0일 때 **비율 Wilson 95% CI**, 차이에 **Newcombe-Wilson 95% CI**를 낸다. U>0이면 각 군의 관측 한계와 차이의 최소/최대 범위만 표시하고 결과가 알려진 행만 골라 CI를 대신 계산하지 않는다. 해당 표본으로 바뀌었다는 제목/건수를 붙이며 전체 프로젝트 표의 CI로 복사하지 않는다.
- 표본이 작거나 0%/100%여도 Wilson을 계산하되 사건/비사건 수·구간 폭을 보인다. `n≥30`만으로 신뢰도를 높이지 않는다. 비율 계산의 근거는 [NIST Wilson 지침](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)이다.
- 위 구간은 전수의 첫 고객 표본 또는 단순무작위 비가중 표본 안의 첫 고객 부분집합에만 적용한다. 층화/결과균형/가중 표본은 별도 설계기반 구간 없이는 기술통계만 낸다. 대표성이 확인되지 않은 자유서술/엑셀 표본은 사례표본 기술통계로만 내고 모집단 CI/전환율을 주장하지 않는다.

계산을 고정한다: 각 군에서 `p=x/n`, `z=1.959963984540054`, `d=1+z²/n`, `center=(p+z²/(2n))/d`, `half=z×sqrt(p(1−p)/n+z²/(4n²))/d`, Wilson 구간은 `[center−half, center+half]`다. n=0은 산출 불가. 두 군의 구간이 `[LA,UA]`, `[LB,UB]`이면 차이 δ=pA−pB의 Newcombe 구간은 `[δ−sqrt((pA−LA)²+(UB−pB)²), δ+sqrt((UA−pA)²+(pB−LB)²)]`이며 출력 시 ×100해 %p로 쓴다. 연속성 보정은 적용하지 않는다. [Newcombe 원문](https://pubmed.ncbi.nlm.nih.gov/9595617/)

이번은 **탐색 분석**이다. 개별 95% 구간은 많은 비교 전체에 대한 동시 95% 보장이 아니다. '유의한 것'만 뽑아 가설을 증명했다고 쓰지 않으며, p값 순위·유의성 별표를 기본 출력에 넣지 않는다. 후속 실험에서 비교·주 지표·다중 비교 처리·최소 개선폭을 사전 고정한다. [ASA 해석 원칙](https://www.amstat.org/asa/files/pdfs/p-valuestatement.pdf)

### 결과마다 표시할 근거 수준

| 축 | 실제 표시할 값 |
|---|---|
| 측정 신뢰성 | 원천/시점 검증 상태, 유효값·미수집·미상률, 분류의 범주별 일치율·오류율 |
| 통계적 정밀도 | 실제 N/전환 수, CI와 폭, 비교 차이와 CI 또는 계산 불가 이유 |
| 안정성 | 월별·첫 제출만·관찰창 변경 시 동일 방향/반전/표본 부족/측정 불가 |
| 일반화 범위 | 전체 제출/원본 보유 표본/특정 폼 노출/수작업 표본 중 해당 범위 |
| 인과성 | 이번 결과는 연관관계. 원인·실험 효과는 미확인 |

종합 판정은 `측정 불가`, `판단 유보`, `후속 검증 후보` 세 가지다. 시점 검증 실패·비교군 부재→측정 불가. 누락/오분류로 결과 반전 가능·넓은 CI·기간별 반전·선별 표본→판단 유보. 측정 조건이 맞고 관찰된 차이가 반복해서 나타나면 후속 검증 후보로 올리되 통계 구간/제약을 함께 싣는다. 결론이 참일 확률 같은 임의 '신뢰도 85점'은 만들지 않는다.

CI가 0을 포함하면 '차이가 없다'가 아니라 '차이의 방향·크기를 확정하기 어렵다'다. 실무적으로 무시할 차이의 허용폭이 정해지지 않았으므로 이번에는 동등성을 선언하지 않는다.

## 7. 사유와 사례 검토

원천 거절/취소 코드와 표준 사유 태그를 별도 열로 유지한다. '기타'를 전부 테스트로 바꾸지 않는다. 실수·테스트·둘러보기, 연락 두절, 예산/견적, 일정·보류, 범위·정책 불일치, 내부 승인·사업 중단 등은 명시적 근거가 있을 때만 매핑한다. 세부 코드는 G0에서 확인하고 값이 없으면 미상이다.

각 사유는 (a) 전체 제출 중 발생 건수/율, (b) 모집 전 거절·취소 전체 중 구성비, (c) 사유가 기록된 부분집단에서의 구성비를 구분한다. 거절만/고객 취소만/합계를 별도로 표시한다. 복수 이유가 있으면 다중 라벨임을 밝힌다. 사유는 결과 설명용이며 같은 프로젝트 초기 준비도의 입력으로 재사용하지 않는다.

사용자 거절 엑셀은 프로젝트 ID로 대조하고 DB와 불일치·누락·기간 밖을 목록화한다. 원천값을 엑셀값으로 조용히 덮지 않는다. 회고 사유만 있으면 작성 시각과 한계를 남긴다.

대표 사례는 수치가 큰 유형뿐 아니라 반례를 포함한다: 정보 적지만 전환, 정보 자세하지만 거절, 첨부 있으나 탐색 목적, 첨부 없어도 기존 자료/자원이 확인된 경우. 사례는 비율을 증명하는 증거가 아니라 분류 오류·해석을 점검하는 자료다.

## 8. 외부자료 연결 계약

고객키·연락처가 필요한 결합은 사내에서만 수행한다. 반출은 프로젝트 ID·필요 파생값·출처·비식별 근거로 제한한다. 기존 [PII 규칙](../../DATA_INTEGRATION.md)에 따라 해시 고객키도 예외로 만들지 않는다. 원본 자유서술은 연락처 스크럽과 필요한 수동 확인 후 사용한다.

근거의 `record_id`/`source_record_ref`도 고객키 반출의 우회로로 쓰지 않는다. 원천 레코드 키가 고객 식별자와 같으면 사내 감사표에서만 관리하고, 분석 파일에는 프로젝트별 비식별 출처 위치를 남긴다.

`source-audit.template.csv.field_id`는 인벤토리 ID(G01/R06 등)다. `external-fields.template.csv.field_id`도 원천 항목 ID이며, 이후 매핑표에서 하나 이상의 CODEBOOK `feature_id`로 변환한다. R05 내부 인력만으로 내부 개발자 변수를 yes로 만들 수 없듯 1:1 강제 매핑하지 않는다. 변환표에는 `inventory_id → source column/question → feature_id → transformation → codebook_version`을 저장한다.

| 외부 입력 열 | 분류 결과 열 | 의미 |
|---|---|---|
| `project_id` | `project_id` | 검증된 정식 프로젝트 연결키 |
| `normalized_value`, `raw_value` | `value`, `raw_value` | 규칙으로 정규화한 값/원본. 미검증 normalized 값은 채택 금지 |
| `value_status` | `value_status` | **CODEBOOK §2 enum만 사용** |
| `known_at_utc` | `known_at` | 해당 정보가 기록된 검증 가능한 시각 |
| `applies_at_utc` | `reported_valid_at` | 회고 진술이 가리키는 시점. known_at 대신 사용 금지 |
| 추출/분류 실행시각 | `measured_at` | 현재 읽은 시각; 과거 known_at을 대체하지 않음 |
| `source_system/record_ref/schema_version`, 생성·수정 시각, `evidence_excerpt` | `evidence[]` | 원천 위치·버전·근거를 보존 |
| `reviewer/reviewed_at_utc/conflict_status` | 검토 메타데이터·`conflict_note` | 해결 전 conflict 값은 통계에서 분리 |

시각에 정밀도가 날짜뿐이면 임의로 00:00 UTC를 사실처럼 넣지 않는다. 원본 문자열·달력 기준·precision을 매핑표에 적고 T0 여부가 경계에 걸리면 `time_unverified` 처리한다. 프로젝트 단위 아닌 응답은 연결 성공·미연결·다대일 충돌 건수를 모두 보고한다.

## 9. 마케팅 가설과 후속 실험

제출자 안에서 전환율이 높다고 그 고객을 광고로 확보하기 쉽거나 전체 계약 수가 늘어난다는 뜻은 아니다. 가설마다 **유입 전에 타깃 가능 / 광고 메시지·랜딩에서 자기선별 가능 / 제출 후 검수에서만 알 수 있음**을 구분한다.

가설 카드에는 대상 정의, 근거 표와 반례, 불확실성, 예상 작동 이유(가설), 실행 채널/메시지, 추가 필요 자료, 반증 기준을 적는다. 예산확보·기존서비스 개선·내부 기술담당자 유무 등은 검토 후보이며 발견된 사실처럼 미리 채우지 않는다. 증거가 약해도 실험 가치가 있는 가설은 **탐색 가설**로 표시할 수 있다.

마케팅 보조 자료 목록: 해당 제출의 UTM/채널·캠페인·랜딩·폼 버전, 방문/폼 시작/제출 분모, 채널별 광고비, 실험 할당/노출. 가입 경로는 프로젝트별 캠페인 유입과 다르다. 자료가 없으면 CPA·채널 효율·유입당 계약 증가를 추정하지 않는다.

후속 실험 설계의 기본: 동일 채널·기간 안에서 타깃/메시지 비교, 사전에 한 주 지표와 관찰창 고정, 모집 전환만이 아니라 **유입당 모집·유입당 90일 계약·계약당 비용**을 함께 추적한다. 표본 수·기간·최소 개선폭은 이번 실제 기초율과 예산을 받은 뒤 계산하며 임의 숫자를 넣지 않는다. 이번 산출물은 실험 후보와 필요한 입력까지이며 실험 집행/광고비 지출은 포함하지 않는다.

사용자는 n8n 워크플로의 노드 구성·실행만 맡고, 분석자는 쿼리·매핑·정합성 검사·집계를 맡는다. 두 검토자는 결과를 가린 분류 교정과 표본 검증을 수행한다. 담당자 확인이 필요한 문항 의미는 추측하지 않고 감사표에 적는다.

- **남은 회사 접근 가능 시간:** 스키마/수집시점/분모 감사와 핵심·쉽게 확보되는 추가 자료 추출, 사외 접근 검증까지 우선 완료. 신규 DB 미도착 때문에 기본 원장 확보를 늦추지 않음.
- **이후 집에서 가능한 시간:** 코드북 핵심 문항 교정·검증, 구조화 특성 전량 집계, 필요한 원문 표본 판독. 실제 확보된 작업 시간에 맞춰 고비용 확장을 제외.
- **9/28 목표:** 불확실성·반례·계약 연결 검토, 전체 결과표와 가설 카드 정리. 추가 DB 접근을 전제로 일정을 잡지 않음.
- **9/29:** 결과 공유. 미확보/미성숙 자료는 명시하고 이후 재관찰 날짜를 제안. 마감을 맞추려고 자료를 추측해 채우거나 약한 결과를 확정하지 않음.

## 11. 실행 검증 시나리오

다음은 분석 구현 시 반드시 확인할 수용 기준이다. 현재 앱 코드를 바꾸는 테스트가 아니다.

- 8/31 KST 마지막 제출은 포함, 9/1 00:00은 본 코호트 제외; 9/3은 최근 코호트 후보.
- 제출+14일 정확히 모집하면 14일 전환, 그 후면 14일 비전환/30일은 별도. 14일 관찰 미성숙은 분모에서 빠짐.
- 모집 후 취소는 전환, 거절 뒤 재개/재제출은 최초 제출·모집 이력 검증 후 처리.
- 현재 모집 상태+모집일 없음, 시각 역전, 날짜-only 경계, 제출일 덮어쓰기 복원 실패는 미상/검사 대상.
- 실수성 고객 제출·숨김/삭제를 기본 분모에서 빼지 않음. 분할/재등록·한 고객 반복 표본의 보조 결과를 따로 냄.
- 초기 본문 행 없음과 실제 빈 본문, 긴 빈 양식, 짧고 구체적인 본문, 첨부 사후 업로드/당시 존재 후 삭제/임시 연결/판독 실패를 구분.
- 내부 인력 있음≠개발자 있음; 예산 숫자≠확보; 법인≠대규모; 제시한 기간≠일정 확정; 무응답≠없음.
- 1:N 첨부/노트/특약/외부답변 JOIN 전후 원장 건수가 증가하지 않음. LIMIT로 꽉 찬 배치 이후 추가 조회와 COUNT 일치 확인.
- 미래 이용 이력·검수 후 상세정보·사후 사유·현재 유효 계약 필터가 T0 특성으로 섞이지 않음.
- N=0은 0%가 아닌 산출 불가, 0/N·N/N의 CI는 너비0으로 만들지 않음. 결과 미상 범위와95% CI를 혼동하지 않음.
- 대표성 없는 판독 표본을 전체로 확대하지 않음. 첫 고객 표본 CI를 전체 프로젝트 CI로 표시하지 않음. 후보 없음도 정상 보고.

관찰연구의 대상·추적·변수·누락·편향·한계를 함께 기록하는 원칙은 [STROBE 체크리스트](https://www.strobe-statement.org/download/strobe-checklist-cohort-studies-pdf)를 참고했다. 통계 방법 참고가 본 데이터 품질의 검증을 대신하지 않는다.
